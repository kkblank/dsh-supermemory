# dsh-supermemory

给 DeepSeek Harness 加上「人格 + 用户画像 + 全局长期记忆 + 项目记忆」的持久记忆插件。

每个会话自动带上记忆，可在 Web UI 里查看、编辑、手动整理；Agent 也能通过
`memory` 工具读写检索。人格/画像/全局记忆按 **人设** 隔离，项目记忆按
**项目根** 隔离。

---

## 它做什么

| 能力 | 说明 |
|---|---|
| 自动注入 | 新建会话时，提示词里自动出现人格、用户画像、全局记忆、项目记忆 |
| 分层注入 | 项目记忆分**常驻 / 目录 / 冷层**三层：常驻照旧注入，冷层不进上下文，中间用一份主题目录（每主题一行）说明"有什么、讲什么、用什么词能捞到" |
| 热度衰减 | 主题与条目的命中按半衰期（默认 30 天）衰减成"有效热度"，只影响排序与展示，**不改分层** |
| 按需读取 | 冷层内容靠 `memory search` 取回；注入时还会按本轮发言从冷层临时捞几条，带轮数冷却 |
| 按人设隔离 | `soul.md` / `user.md` / `global-memory.md` 每个人设一份 |
| 按项目隔离 | `<项目根>/.dsh/memory/project-memory.md`，不同项目互不可见 |
| 单条快照 | 记忆内容变化后下一次请求即生效，历史里始终只有一条最新快照，不随轮次累积 |
| Web 面板 | 侧栏「记忆」图标 → 独立面板，切换人设/项目、编辑保存、mtime 冲突检测、**分层概览 + 记忆热度表** |
| 主题体系 | 盘上还没有任何主题时，整编会一次性把主题建起来（条目分类 + 主题表 + 别名）；建好之后不再重复引导 |
| 设置页 | 只读概览：目录、预算占用、触发阈值、最近整理 |
| 手动整理 | 每 N 轮 / 上下文压力超阈值 / 手动按钮触发，**只写项目记忆** |
| 整理模型可选 | 面板里从已配置模型中选择整理用的模型，或跟随当前会话 |
| `memory` 工具 | Agent 可 list / read / search / append / replace / digest |
| 预算降级 | 各段预算**各自独立**降级：项目段超额只影响项目段，不会把全局记忆一起削掉 |
| 分批整编 | 记忆长到 30 条后，整编从「一次重写整份」改为**按主题分批降精**，单轮规模有上限，不会因记忆变长而撞输出预算 |
| 压缩补偿 | **只在快照真被压缩摘要吞掉时**，下一轮自动重写完整记忆快照；压缩压的是别处则不重写，digest 不变也不会多出第二条 |

## 写入策略（v2 起）

| 分区 | 自动整理 | Agent 工具 | 用户手动 |
|---|---|---|---|
| 人格 `soul` | ❌ 永不 | 仅当用户明确要求改人设，且带 `confirmSoul: true` | ✅ |
| 用户画像 `user` | ❌ 永不 | ✅ 但只写用户明确陈述的偏好/事实 | ✅ |
| 全局记忆 `global` | ❌ 永不 | ✅ 同上 | ✅ |
| 项目记忆 `project` | ✅ 唯一自动写入的分区 | ✅ | ✅ |

自动整理只在**项目记忆**上工作：它读最近对话，提炼与当前项目相关的新增约定/决策/坑，
追加写进 `<项目根>/.dsh/memory/project-memory.md`。

## 安装

在 DSH 的 `web` profile 里安装本目录（工作区绝对路径）：

```js
plugin_manager({ action: 'install_bundle',
                 target: '/absolute/path/to/dsh-supermemory' })
```

安装后确认返回 `application: applied`，然后刷新页面。

## 数据放在哪

```
$DSH_HOME/supermemory/
  personas.json                    # { version, current, personas:[{slug,name,createdAt}] }
  personas/<slug>/
    soul.md                        # 人格设定
    user.md                        # 用户画像
    global-memory.md               # 跨项目长期记忆
  settings.json                    # { digestProvider, digestModel }
  projects.json                    # 仅记录 lastSeenAt，不作为项目列表来源
  runs.jsonl                       # 最近整理报告（最多保留 200 条）
```

```
<项目根>/.dsh/memory/
  project-memory.md                # 该项目专属记忆
  pitfalls.md                      # 同目录全部 .md 一视同仁进检索范围（文件名不限）
  usage.json                       # 检索与预取的命中热度，按条目与主题名记账（只存 hits + last，衰减分现算）
  history/                         # 整编前的原文快照
```

- **人设**：面板下拉里的条目，可新增。每个拥有独立的 soul/user/global。
  首次安装自动创建 `Default` 人设。
- `slug`：人设名里保留 Unicode 字母数字（含中文），其它字符折叠为 `-`，
  上限 48 字符；空/全非法回退 `default`。所以「工作助手」会得到
  `personas/工作助手/`。
- **项目列表自动同步宿主工作区**（`workspaceRegistry`），不需要手动添加；
  有几个工作区项目就有几份项目记忆。
- 项目根：从会话 cwd 向上找 `.git`，找不到则用 cwd 本身。

## 文件格式

四个文件统一格式：

```md
# 全局长期记忆

<!-- 由 dsh-supermemory 维护；可直接编辑。 -->

## 条目

- 2026-11-10T10:00:00.000Z · source:user-request
  内容第一行
  内容第二行
```

## 注入长什么样

系统提示里加一段人格 + 画像（`supermemory:persona` section），
对话里加一条可替换的快照消息：

```
<supermemory>
## 全局长期记忆 (global)
...
## 项目记忆 (project: <项目根名>)
...（常驻层条目的正文）

### 主题目录
- 注入机制（4条）：这个主题大致在讲什么 → 注入, 快照, surface, append
- 面板路由（2条）：… → 面板, client, 404
...
冷层条目用 memory 工具按需检索（action=search, scope=project）。

## 本轮相关记忆
...（按本轮发言从冷层临时捞回的若干条，冷却期内保持不变）
</supermemory>
```

- **人格与画像不在这条消息里**——它们只走系统提示那一份，快照正文只含全局与项目两段，
  避免同一份内容每轮被注入两遍。
- 内容里的 `</supermemory>` 会被转义（在 `<` 后插反斜杠），防止提前闭合冲破结构。
- `{{...}}` 按字面量保留（section 用 `interpolate: false`）。
- **各段预算各自独立**：`projectCoreMaxBytes` 管常驻正文、`projectIndexMaxBytes` 管主题目录、
  冷层临时捞取另有上限。哪一段超额只在那一段内部降级，**全局记忆永不被项目段拖累**。
- 常驻正文装不下时，被挤出的条目**临时**折进目录（标注「本轮被预算挤出」并给出取回方式），
  下一轮预算宽裕会自动回来——这是渲染期的临时折叠，不写回磁盘、不改变条目的分层身份。
- 目录里的每个主题一行同时给出检索别名，让模型知道用什么词能把冷层内容捞出来。

**压缩之后**：宿主压缩会写一条 checkpoint，用 `surfaceOp: replace` 把整段
surface 区间换掉，本插件的快照可能被一起吞掉。因此每轮 pre-step 都做一次
重同步判定——快照已不在 surface 上，或最近一次压缩晚于快照，就重写一条。
重写后的正文与 digest **逐字节不变**，不往记忆里掺「上下文已压缩」这类提示；
收敛后不会反复重写。快照存活判定优先看 `session.surface.nodes`，拿不到时
按压缩事件的 `shadowedSeqs` 排除，两者都没有才退回日志顺序。

## 配置

在 `cordis.patch.yml` 的 `supermemory` 行里改；全部字段 `.volatile()`，设置页改动即时生效。

| 字段 | 默认 | 说明 |
|---|---|---|
| `enabled` | `true` | 总开关（`false` 时不注入、不注册工具与面板） |
| `personasRoot` | 空（= `$DSH_HOME/supermemory/personas`） | 人设根目录 |
| `projectDirName` | `.dsh/memory` | 项目内目录 |
| `projectFileName` | `project-memory.md` | 项目记忆文件名 |
| `systemPromptMaxBytes` | `12000` | 人格+画像进系统提示的上限 |
| `injectMaxBytes` | `24000` | 全局+项目注入消息的上限 |
| `autoDigest` | `true` | 自动整理开关 |
| `digestEveryTurns` | `5` | 每 N 轮整理（0 关闭） |
| `digestPressureRatio` | `0.75` | 上下文压力阈值（0 关闭） |
| `digestMaxInputBytes` | `120000` | 整理请求输入上限 |
| `digestMaxOutputTokens` | `3000` | 整理输出上限 |
| `digestProvider` / `digestModel` | 空 | 默认整理模型；面板里选的值优先 |
| `digestWritableScopes` | `['project']` | 整理可写的分区（v2 硬限制为 `project`） |
| `injectIntoSubagents` | `false` | 子智能体是否带记忆；默认**不带**，需要时显式配 `true` |
| `compactionRecall` | `true` | 快照被压缩吞掉后的自愈与补偿重写；`false` 只关掉补偿，**快照丢失后的基本自愈仍保留**。**与下面 `projectRecall*` 的按轮预取无关，只是撞名** |
| `digestConsolidate` | `true` | 整编模式开关：条目数或体积达标后，整理从"追加"升级为"重写整份目标态" |
| `digestConsolidateMinEntries` | `20` | 触发整编的条目数 |
| `digestConsolidateMinBytes` | `12288` | 触发整编的体积 |
| `digestConsolidateCooldownMs` | `21600000` | 两次整编的最小间隔（6 小时） |
| `digestConsolidateMaxOutputTokens` | `12000` | **整编输出上限，推理模型必读**：思考内容也算输出并先扣这份预算，且**与待重述的记忆规模成正比**。本机实测记忆长到 32 条 / 12KB 时需 ≈55k tokens，故显式配到 `60000`；配小了症状是"正文写完前思考就被截断、整理失败"。**分批整编（下面 5 项，默认开）会把单轮规模压下来**，记忆继续增长时优先靠它，而不是继续调大这个数 |
| `digestTieredConsolidate` | `true` | 分批整编总开关；`false` 退回「每次都整份重写」 |
| `digestTier2MinEntries` | `30` | 进入分批的条目数阈值（未达则整份重写，行为与旧版一致） |
| `digestTier3MinEntries` | `60` | 改用更大批的条目数阈值；必须大于上一项 |
| `digestTier2BatchTopics` | `5` | 每批最多处理多少个主题（T2 档） |
| `digestTier3BatchTopics` | `8` | 每批最多处理多少个主题（T3 档） |
| `tieredInjection` | `true` | 分层注入总开关；`false` 退回整份项目记忆全量注入 |
| `projectCoreMaxBytes` | `16384` | 常驻层正文预算，超额条目临时折进目录 |
| `projectIndexMaxBytes` | `3072` | 主题目录预算 |
| `projectRecallMinRounds` | `3` | 冷层临时捞取的最小间隔轮数（防每轮换血） |

> 整编阈值与预算属于**运维旋钮，只从 `cordis.patch.yml` 读，面板不提供**；
> 显式写出的值会压住代码里的默认值——改默认值对已显式配置的机器无效。

> 旧字段名 `presetsRoot` 仍被接受，等价于 `personasRoot`。

**整理模型优先级**：面板选择（`settings.json`）→ 配置里的 `digestProvider/Model`
→ 当前会话路由 → 宿主默认模型。每层要求 provider 与 model 同时非空。

## `memory` 工具

| 参数 | 说明 |
|---|---|
| `action` | `list` / `read` / `search` / `append` / `replace` / `digest` |
| `scope` | `soul` / `user` / `global` / `project` |
| `query` | `search` 时必填，检索词；自动分词并补中文相邻二元组，按相关性排序。不支持正则 |
| `content` | `append` / `replace` 时必填 |
| `reason` | 写入原因，写进条目元数据 |
| `confirmSoul` | 写 `soul` 时必须为 `true`；否则返回 `SOUL_CONFIRM_REQUIRED` |

`project` 作用域的项目根由会话 cwd 自动解析，**不接受模型传入任意路径**；
所有路径穿越都被拒绝。

`scope: project` 的检索覆盖 `<项目根>/.dsh/memory/` 下**全部 `.md`**（含 `pitfalls.md`
这类自建记录文件，以及 `history/` 里的整编前快照，后者仅在别处无命中时兜底再搜）；
人格、画像、全局记忆仍各只读自己那一个文件。
每次检索与每次冷层捞取的命中会按条目与主题名计入 `usage.json`。

**热度只是参考信号，不决定分层**（v12 起明确）：

- 热度按**指数衰减**折算成有效热度——`log(1+命中数) × 0.5^(距今天数/半衰期)`，半衰期默认 30 天。
  裸命中数分不出「昨天用过 20 次」和「三年前用过 20 次」，而冷热的意义全在时效。
- 衰减分**不落盘**，`usage.json` 仍只存 `{ hits, last }`；每次现算是为了不产生「每轮写盘」。
- 热度参与两件事：**core 内部排序**（预算紧张时决定谁先被临时挤出）与**面板/整理器展示**。
  面板的分层概览里有一张热度表，**主题级与条目级合并显示**：
  - 主题级只在整理器建过主题表之后才有；在那之前每一行都是**具体条目**，所以表头叫「记忆热度」
    而不是「主题热度」，免得「主题 0 个却有十几行」看起来像 bug。
  - 条目级显示**正文首行前 40 字**（悬停看完整条目），不再显示十六进制 id。
  - **映射不到正文的孤儿热度不显示**：整编改写正文会让条目 id 换代，旧 id 的热度会永远留在
    `usage.json` 里。它们既看不懂也排不上用场，只在展示层过滤，**不从盘上真删**——
    条目可能临时不在（切人设、项目目录移动），真删会把还能复用的热度丢掉。
  - 表格限高 132px 并内部滚动，不会把项目记忆正文挤没。
- **它绝不改 `tier`**：盘上某条是 core 还是 cold，只由整理模型在整编时写入。
  这一点有回归测试钉死（`test/heat-decay.test.js`）。
- 降级还有一层**护栏**：`source` 为 `user-request` / `lead-summary` 的条目、含明确硬约束
  （「不得 / 必须 / 禁止」等）的条目、以及技术栈与环境约定类条目，整理器**一律不许降到冷层**，
  不管热度多低。

## 斜杠命令

- `/remember [scope] <内容>` —— 等价 `memory append`，默认 `global`
- `/remember soul --confirm <内容>` —— 改动人格需要 `--confirm`
- `/memory-digest` —— 立即整理一次（只写项目记忆）

## 停用

把 `cordis.patch.yml` 里 `enabled` 改成 `false`，或在插件管理页禁用 `supermemory` 行。
停用后不注入、不注册工具与面板。

## 已知边界

- 不做向量/embedding 语义检索（纯 md + 词法检索；中文按相邻二元组近似分词）。
- **条目的分层身份由整理器判断，不是算法自动分的**：判高了浪费预算，判低了要靠热度慢慢升回来。
  热度只影响渲染排序与展示，**永远不会自动把某条降级或升级**——刻意的设计：久不用的旧项目记忆
  可能某天被突然翻出来用，自动降级等于让它在那之前"看不见"。
  主题表也只由整理器维护，写入侧不接受自定义主题名——自由命名会让热度记账断链。
- **主题体系有一次性冷启动**：盘上还没有任何主题时（条目也没写过 `topic`），整编会追加一段
  引导让模型一次性把主题建起来——否则「主题表靠条目的 topic 汇总」与「topic 优先复用主题表里
  已有的名字」这两条会互相等待，模型什么都不写。主题体系建好之后这段引导不再出现，
  以免每轮重新分类把主题名改乱。
- **主题表围栏里的行不参与检索结果**：它们是目录文字，不是记忆。尤其孤儿主题（表里有名
  但没有任何条目在用）的别名若参与匹配，「搜一个词」会只拿到一条读不出原文的空结果。
  `pitfalls.md` 这类手写文件的前言与目录表格**不受影响**，仍可正常检索。
- **主题名是热度记账的锚点**：整理器给同一件事换了个名字，那份热度就挂在旧名字上从零重新开始。
  面板的「孤儿主题」非空是这个情况的现成信号。
- **冷层内容没人检索就等于不存在**：它依赖模型主动搜或本轮发言恰好命中；
  检索不到又确实重要的内容应留在常驻层。
- 压缩补偿只重发快照，不改写压缩摘要，也不保证摘要本身保留了记忆内容。
- **快照重写会尽量少写**：快照每重写一次，它之后那半段上下文的缓存就全废。所以
  ① 五维内容都没变时不写；
  ② **只有「本轮相关记忆」变了、正文一个字没变时不写**——正文是最长最稳定的部分，
  为换 2KB 预取小节重写整块不划算。旧快照已有预取内容时才延后，旧快照没有预取时
  必须写（否则预取永远出不来）。
  每次重写的归因（`reason` + 具体哪一维变了）落在快照的 `source.rewrite` 里，可事后核对。
- **「本轮相关记忆」不会因为某轮检索不到就消失**：短句（「好」「继续」）常检索不出冷层候选，
  若这时清空，下一轮又命中，这段内容就会在有→无→有之间翻转——同一批记忆时有时无，
  模型无从判断该不该依赖。所以无候选时沿用上轮，直到冷却轮数到了才换。
  预取为什么没内容也有明确原因字段可查（拿不到用户输入 / 没条目 / 零命中 / 无候选 / 冷却中）。
- **分批整编是按主题轮流的**：一轮只整理一批主题，其余主题原样保留，多轮之后才覆盖全部。
  因此「刚整理完」不等于「整份记忆都刚被梳理过」；单轮看到的改动范围可能只是其中几个主题。
- 不做文件版本历史与回滚。
- 不做敏感信息过滤。
- 不跨机器同步，不做记忆导入导出。
